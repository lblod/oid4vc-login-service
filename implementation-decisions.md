This page chronicles the decisions that we took while implementing verifiable credentials in the decide project.

Currently we have only implemented OID4VCI and OID4VP, which covers human-to-machine interactions. 

For Machine-to-machine interactions we planned to use the Eclipse Dataspace Decentralized Claims protocol as recommended by DSSC: https://dssc.eu/space/BVE2/1071254873/Building+on+Top+of+Foundational+Technical+Standards#Eclipse-Dataspace-Decentralized-Claims-Protocol

However, when checking in with our DS4SSCC coaches, Gernot Boege told us that

>    No, the DCP is not part of the recommended standards and is not in the scope of this project
>    Some pilot's have decided to chose the EDC stack which raises challenges to be solved

We will therefore hold-off on implementing a machine-to-machine solution. Partners who want such a solution will have to develop it themselves.

# OID4VC Issuance

We decided that we wanted to use the OID4VC issuance protocol to issue credentials to users so that they can log into our systems (or other systems that trust us as a credential issuer). The reason is that this way, we can have different parties in the distributed data space be trusted issuers of roles in the dataspace. That way, issuers can exist for Gent and Freiburg for instance and a certificate generated by Freiburg can allow access to the dataset of Gent if Gent trusts this issuer. 

This approach can then also be reused to develop VC issuers on an ABB level for other LBLOD data spaces and applications even outside of the Decide project.
## Wallets considered

We had a look at the EBSI recommended wallets. This list provided interesting candidates, but we could only examine the Open Source wallets. Many links were also to company or government pages without providing a link to the implementation itself.

In the end the wallets we examined for testing were:

- https://github.com/walt-id/waltid-identity (only supports storing the certificate in a wallet, for presentation it supports an older version of the spec without DCQL)
- https://github.com/animo/paradym-wallet (supported, BUT returning certificates according to a slightly older version of the spec, fairly easy to change later when properly supported)
- https://github.com/simpleidserver/SimpleIdServer (seems to have implementation issues or at least only support a very early version of the spec)
- https://github.com/Sphereon-Opensource/mobile-wallet (not supported: claims our sd-jwt-vc certificate is invalid, not debugged further)
- https://github.com/eu-digital-identity-wallet/eudi-app-android-wallet-ui (EUDI wallet initiative, very much still in implementation/demo phase during the DECIDe project. Discussed in separate section.)

## Specification draft status

At the start of sprint 37/3, where we started implementation, we noticed that the specification was in fact only in a draft state. The final version of the spec was released on 2025-09-16, so even during that sprint. 

We noticed that many wallets were quite behind on the implementation of this spec, e.g. draft version 11 and 13 were popular while 17 was already out. There are major differences in these versions that we had to work around while implementing (e.g. no credentials wrapper property in the credentials response).

The impact of this problem is not to be underestimated. E.g. to be able to support issuing credentials to the Paradym wallet (date: 2025-09-25, version 1.14.3 (63)), we had to remove the spec-mandated property credentials in the response and replace it with credential. This was fixed by an update of the Paradym app in november that brings the app fully up to spec version v1.0 (at 2025-12-08, running version 1.17.0 (75), which works without spec workarounds).

It is our hope that, now that the specification has made it to a v1.0 status, multiple wallets will soon reach feature parity with the specification and the number of supported wallets will therefore grow.
## Only support pre-authorized flow

The only flow we care about right now is the pre-authorized flow. We will use it to hand out a credential to a party that is already signed in through an existing authentication/authorization system (e.g. ACM/IDM or any other authentication/authorization mechanism used by a partner). From then on, this user can use their credential to log in to our system or systems that trust our issuer.

Our authorization codes are 16 bytes large and have a 1 minute TTL, our authorization tokens are 512 bytes large and have a 24h TTL. Both are generated in a cryptographically random fashion.
## No transaction code

Since we don't want to increase the scope by setting up a secondary channel to share the transaction code for the credential (mail, text message, ...), we choose not to use a transaction code in this PoC.
## No support for LDP-VC, using SD-JWT-VC instead

None of the wallets we found supported LDP-VC credentials, which would have given us the most flexibility in terms of which content we express in our credentials. As it had the highest adoption rate, we went for SD-JWT-VC instead. This does give us selective disclosure of the contents of the credential, but in our use cases this is not directly relevant yet. It may become relevant if we decide to award multiple roles for different systems in the same credential and want to selectively disclose roles depending on the system we want to log in at.

While this does rule out LDP-VC credentials in the scope of OID4VC (at least for now), we can still use them for other purposes. For instance, we could provide DCAT descriptions of distributions as an LDP-VC credential, so users know the endpoint has not been tampered with.
## did:web

Our issuer uses a did:web with a EdDSA (ED25519) verification key. EdDSA gives us higher security and higher performance than ES256. It used to have lower support than ES256 but this problem has now mostly disappeared.

We chose did:web because it has an additional level of security (through HTTPS) that did:key does not have and it also allows us to rotate our keys, should the need arise.
## Binding of cryptographic key

Some wallets require the binding of the cryptographic key of the holder to the certificate, initially we will not require this to keep the scope manageable. If there is time, we will require it as it is recommended.

The only wallet that is still somewhat spec-compliant at this point is the Paradym wallet and while it allows receiving credentials that don't support the binding of a cryptographic key, it refuses to present them as it complains that metadata provided, but credential has no 'cnf' claim to create a KB-JWT from. It turns out that this is not the fault of our api, as we're not providing metadata, but the metadata is added by the app itself. As a result, we DID have to implement key binding in our certificates.

We only support the jwt proof type for now to keep the scope contained. We require the wallet to provide us with a did:key or did:web and use it to validate the jwt proof they provide when requesting a credential. We require this jwt to use either the EdDSA or ES256 algorithm, again to keep the scope somewhat contained.

During development, Paradym added an additional constraint, requiring that the vc issued should be bound to the DID they presented, not just the jwk that corresponds to it. This is a respectable constraint, but it did break our approach as we bound to the jwk instead. This also meant that during verification, we now need to check for the kid instead of the jwt in the credential to verify that it was signed by the same party.
## Nonce

To guard against replay attacks where an attacker obtains the proof and uses it to create duplicate credentials, OID4VC issuance allows the definition of a nonce endpoint. This is required by some wallets. 

To support the Paradym wallet, we added a nonce endpoint and also validate the use of this nonce in the issuing process.
## Certificate contents

The contents of the certificate is kept very minimalistic right now (we have to, as it's a sd-jwt-vc so it's not meant to share linked data). In the certificate, we share the did of the owner, and their authorization groups for the decide project. Since it's a selective disclosure credential, we can extend this to include groups from other data spaces if we'd like, but there seems no real reason to do so at this time.

# OID4VP

The OID4VP protocol is the corresponding protocol to OID4VC issuance that handles the presentation of the verifiable certificates from the wallet to the verifier.
## Specification draft status

The same remark regarding the specification being in draft status holds for the OpenId for verifiable presentations spec. While this specification hit v1.0 a couple of months earlier than its OID4VC issuance cousin, at times we still had to implement things slightly differently than the latest version of the spec demands.
## DCQL

The final version of the spec mandates the use of DCQL. However, this is a fairly new part of the spec and previously it also allowed support for the use of a presentation_definition , this originally was the only supported option. As a result, some wallets don't have support for DCQL yet (e.g. the walt.id wallet).

This means that where we had two working wallets up until the awarding of a credential, the presentation of a credential brings this down to a single wallet. We go from walt.id and paradym to only paradym (and even for paradym, we needed to return the credentials in a non-spec compliant way, but this is an easy feature flag to toggle once the wallet catches up).

After our first implementation Paradym updated their application and is now completely inline with the spec v1.0.
## Key Attestations

The issuer can define certain requirements on the keys used by wallets and their security properties. In the scope of this PoC, we don't do this yet to keep the scope small. 
## Nonce

In the case of OID4VP the nonce provided to the wallet during the presentation process is also validated when the verified presentation is validated.
## Response encryption

The direct_post.jwt response mode was chosen because it's mandated by the Paradym wallet, which was the wallet that was most up to date with the spec at the time of this writing.

The verifier only provides one ephemeral key as part of its client_metadata. The algorithm chosen was ECDH-ES with a P-256 curve because this is the most supported type. We could add more keys to the jwks list in our client_metadata to offer even broader support but opted to keep the scope small for now instead.

There is also no reason to add multiple keys to the jwks list to support key rotation as a new key is generated for each interaction.

To support the Paradym wallet, we had to deviate slightly from the spec here as well, in the sense that we return the following in our client_metadata instead of giving multiple options with encrypted_response_enc_values_supported as mandated by the spec:

- authorization_encrypted_response_alg: 'ECDH-ES',
- authorization_encrypted_response_enc: 'A128GCM',

Ephemeral keys shared by our verifier have a 10 minute time to live.
## Client_id as did in client_metadata

Our client id is a did:web id and is included as such in the client_metadata. However, note that to support the paradym wallet, we had to remove the spec-mandated decentralized_identifier: prefix from our client_id in the client_metadata. (no longer true with Paradyms 1.0 update).
# Supporting the EUDI wallet

We were recommended the EUDI wallet as a wallet to store our credentials. This wallet is still in development at the time of this writing (2025-12-08), and the path to support this wallet has been rough.
## No DID support

While DIDs are a key technological component of DSSC, the EUDI wallet does not support it and a heated discussion was held on their GitHub that shows disdain for the technology. This thread ends with a statement that for SD-JWT-VC providers, DIDs could be supported and that this would be added to the EUDI Architecture Reference Framework, but no such change has been made. The ticket linked above stating that the ARF does not support DIDs is also almost a year after this statement.

It is peculiar that DIDs are pushed as a key component in DSSC but then completely disregarded by the EUDI wallet.

To mitigate this, we have taken the following actions when implementing our issuer/verifier service:

    allow the use of jwk as a cryptographic binding method during issuance. The jwk is then transformed to a did:key for compatibility.

    allow the verifier to be configured using a x509_hash client identifier prefix instead of a decentralized_identifier prefix. 

This last step required quite a lot of extra effort and is discussed in its own subsection.
## X509 support

As stated before, the EUDI wallet did not support DID identifiers. Our verifier used a did:web to identify itself and establish trust, which therefore was not enough. We pivoted to x509_hash, which was supported by the EUDI wallet.

This required us to bind our issuer to the https certificates provided by our issuer Letsencrypt. However, the EUDI wallet has some additional restrictions on these certificates:

    we had to add the certificates to the app manually, this means that we need to build the app specifically for our database and keep it updated when our certificates are rotated.

    (2025-12-08) The EUDI wallet requires the extended key usage "1.0.18013.5.1.6" for the verifier's certificate, which is mentioned in the mdoc context as required for driver's license verification, but in our SD-JWT-VC context it is unnecessary. Other users already flagged this as an issue. As our certificate issuer Letsencrypt does not allow setting this extended key usage and as it is not mandated by the spec, we removed this constraint in the version of the EUDI wallet that we built.

    (2025-12-08) The EUDI wallet requires SHA-1 encoding when validating the SubjectKeyIdentifier of the certificate. However, SHA-1 has fallen out of favor and is, for instance, no longer used by Letsencrypt, who uses SHA-256. Other users also flagged this as an issue. To continue with our PoC, we also added SHA-256 support to our build of the EUDI wallet.

All of these changes required us to create our own build of the EUDI wallet. The code for that is available as a fork here: https://github.com/Rahien/eudi-app-android-wallet-ui. Even if issues 2 and 3 are fixed, the nature of the validation process requires users to maintain their own fork of the EUDI wallet to hold the set of trusted certificates.

This is already flagged as an issue on the EUDI wallet's GitHub, with other developers suggesting that it would be better to allow adding trusted issuers in the UI of the app OR simply not require the issuer to be trusted by default (and showing it as untrusted to the user).
## No Cookiejar

The EUDI wallet app does not have a cookiejar to track cookies sent by the server. As we do have our own build of the app, we could have added this cookiejar, but we decided against this because it means other wallet apps may make this decision. We configured our application to work without depending on the session of the wallet being reused. 

This means that a nonce can be claimed by another client during the issuance process. We made this configurable in our service, but as our nonce has 16 bytes of randomness, the odds of this happening are small.
## CRL https enforcement

The EUDI wallet app enforces that the CRL of the X509 certificate issuer is hosted over HTTPS and refuses to download it over HTTP. Other users also flagged this issue. As we were already making our own build of the wallet app now, we added the Letsencrypt CRL url to an exception list so it can be fetched over HTTP. (Note Letsencrypt actually does also host the CRL over HTTPS, but the certificate lists it as HTTP, so if the wallet were to upcycle HTTP urls for CRLs to HTTPS, that would also work).
## Wallet Attestation

We currently don't want to support wallet attestation in our issuer to keep the scope contained. However, the default implementation of the EUDI wallet (2025-12-11) seems to require it. One can set client attestation to None per issuer when building the app, however, there seems to be a bug (2025-12-11) where it doesn't want to continue with the flow unless we falsly claim a value for dpop_signing_alg_values_supported in our issuer's authorization_metadata. We added an environment variable that allows us to lie about that value. We also created an issue with the EUDI team.
